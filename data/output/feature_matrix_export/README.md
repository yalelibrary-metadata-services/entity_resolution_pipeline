# Entity Resolution Feature Matrix Export

Feature matrix and embedding vectors for the labeled ground-truth pairs used by
the Yale Library entity resolution pipeline. Person entities extracted from
MARC 21 catalog records are compared pairwise; each pair carries engineered
similarity features (computed from vector embeddings, temporal regexes, and
taxonomy classifications) plus a human-labeled `match` verdict.

Everything here is self-contained: no access to the pipeline, its checkpoints,
or the Weaviate vector database is required.

## Provenance

| | |
|---|---|
| Source | Yale BIBFRAME catalog (MARC 21), ground truth `labeled_matches.csv` |
| Generated by | `export_feature_matrix.py` (repo root of `entity_resolution_pipeline`) |
| Embedding model | OpenAI `text-embedding-3-small`, 1536 dimensions |
| Feature scaling | `LibraryCatalogScaler`, fitted during the training stage (see `*_scaled` below) |
| Manifest | `export_manifest.json` — exact counts, feature list, creation timestamp |

To regenerate (requires the pipeline environment, its checkpoints, and a
running Weaviate instance):

```bash
source venv/bin/activate
python export_feature_matrix.py --config config.yml
# options: --ground-truth <csv>  --fields person,composite  --skip-vectors  --output-dir <dir>
```

## Files and data model

```
feature_matrix.parquet   49,766 rows   one row per labeled entity pair
entity_fields.parquet    18,746 rows   personId -> (field, hash) join table
embeddings.parquet        9,404 rows   one row per unique (hash, field): text + vector
export_manifest.json                   provenance and counts
```

Vector data exists **only** in `embeddings.parquet` (its `vector` column,
Arrow type `list<float>`); `feature_matrix.parquet` and
`entity_fields.parquet` contain no vector columns — only strings, scalars,
and the label. Vectors are stored once per unique string (keyed by the
pipeline's xxHash of the string), not once per entity — e.g. the 2,535
entities share only 185 distinct person name strings. To attach vectors to a
pair, join:

```
feature_matrix.left_personId ──┐
                               ├──> entity_fields.personId ──> (field, hash) ──> embeddings.hash + field
feature_matrix.right_personId ─┘
```

### feature_matrix.parquet

One row per labeled pair. 40,220 matches, 9,546 non-matches.

| Column | Type | Description |
|---|---|---|
| `cluster` | int64 | Ground-truth cluster the pair was sampled from |
| `identity` | double | Identity ID within the cluster (NaN on non-match rows) |
| `names` | string | Person name variants in the cluster, e.g. `Schubert, Franz. Schubert, Franz, 1797-1828.` |
| `left_personId`, `right_personId` | string | Entity IDs, format `<recordId>#<agentTag>`, e.g. `16044091#Agent700-32` |
| `match` | bool | Human-labeled verdict: same real-world person? |
| 8 feature columns | double | Raw feature values in [0, 1] (below) |
| 8 `*_scaled` columns | double | Same features after the fitted production scaler — **this is what the classifier consumes** |

Feature columns, in classifier input order:

1. `person_cosine` — cosine similarity of person name embeddings
2. `taxonomy_dissimilarity` — domain-classification distance; categorical levels {0.0, 0.15, 0.4}
3. `composite_cosine_squared` — squared cosine of full-record composite embeddings
4. `has_related_work` — binary: both entities have a relatedWork field
5. `birth_death_match` — binary: birth/death years match within ±2 years
6. `confidence_amplifier_polynomial` — polynomial transform `0.5x³ − 0.3x² + 0.8x` of composite similarity
7. `person_title_interaction_cubic` — cubic person×title interaction term
8. `provision_similarity` — publication place/date similarity (custom feature)

Raw vs scaled: the scaler clips each feature's upper tail at a per-group
percentile (person 98th, composite 90th, default 95th) and rescales to [0, 1];
binary features are passed through as exact {0, 1} and `taxonomy_dissimilarity`
is preserved verbatim. Use `*_scaled` to reproduce classifier behavior; use raw
for your own modeling. All 16 value columns for one row
(`16044091#Agent700-32` vs `9356808#Agent100-11`, match = true):

| feature | raw | scaled | |
|---|---|---|---|
| `person_cosine` | 0.916181 | 0.805310 | stretched (98th-pct clip) |
| `taxonomy_dissimilarity` | 0.000000 | 0.000000 | preserved verbatim (categorical) |
| `composite_cosine_squared` | 0.205403 | 0.437393 | stretched (90th-pct clip) |
| `has_related_work` | 0.000000 | 0.000000 | unchanged here |
| `birth_death_match` | 0.000000 | 0.000000 | preserved exactly (binary) |
| `confidence_amplifier_polynomial` | 0.331406 | 0.455738 | stretched (95th-pct clip) |
| `person_title_interaction_cubic` | 0.130299 | 0.256815 | stretched (95th-pct clip) |
| `provision_similarity` | 0.159327 | 0.332445 | stretched (95th-pct clip) |

## Usage examples

### pandas

```python
import pandas as pd
import numpy as np

fm  = pd.read_parquet("feature_matrix.parquet")
ef  = pd.read_parquet("entity_fields.parquet")
emb = pd.read_parquet("embeddings.parquet")

# Classifier-ready matrices
feature_cols = [c for c in fm.columns if c.endswith("_scaled")]
X = fm[feature_cols].to_numpy()
y = fm["match"].to_numpy()

# Attach the person-name vector for each side of every pair.
# NB: join on hash AND field — the same string (hence hash) can appear
# under more than one field type.
person_vec = (
    ef[ef.field == "person"]
    .merge(emb.loc[emb.field == "person", ["hash", "vector"]], on="hash")
    .set_index("personId")["vector"]
)
fm["left_person_vector"]  = fm.left_personId.map(person_vec)
fm["right_person_vector"] = fm.right_personId.map(person_vec)

# Sanity check: cosine of the person vectors reproduces the person_cosine feature
row = fm.iloc[0]
a, b = np.array(row.left_person_vector), np.array(row.right_person_vector)
cos = a @ b / (np.linalg.norm(a) * np.linalg.norm(b))
print(cos, row.person_cosine)   # ~0.9162 both
```

### DuckDB / SQL

```sql
-- Pairs with identical names that are NOT the same person, with their composite texts
SELECT f.left_personId, f.right_personId, f.composite_cosine_squared,
       le.text AS left_composite
FROM 'feature_matrix.parquet' f
JOIN 'entity_fields.parquet' lf
  ON lf.personId = f.left_personId AND lf.field = 'composite'
JOIN 'embeddings.parquet' le ON le.hash = lf.hash AND le.field = 'composite'
WHERE f.person_cosine > 0.999 AND NOT f.match
LIMIT 10;
```

## Caveats

### Pair sampling is cluster-based, not random

Pairs were not drawn randomly from the catalog. They come from clusters of
entities that already share similar name strings, because that is the
pipeline's candidate space — entities with dissimilar names are never
compared at all. Two consequences:

- The non-matches are **hard negatives**: different people who share a name
  (see the example below), not arbitrary unrelated entities. This data cannot
  tell you how a model behaves on easy pairs; there are none.
- The 81% match / 19% non-match balance is an artifact of ground-truth
  labeling, **not a population estimate**. In the full catalog the
  overwhelming majority of possible pairs are non-matches, so do not
  calibrate probabilities or estimate production match rates from this
  class balance.

### `identity` is meaningful only on match rows (NaN on non-matches)

`identity` names *which* real-world person a pair resolves to, so it can only
be filled when the two entities are the same person. A non-match row asserts
"these are two different people" — there is no single identity to record, and
the field is NaN by construction, not from missing data. Cluster 9 ("Schubert,
Franz") contains two real people and shows the pattern:

| cluster | identity | left_personId | right_personId | match | who |
|---|---|---|---|---|---|
| 9 | 0.0 | 16044091#Agent700-32 | 9356808#Agent100-11 | true | composer ↔ composer |
| 9 | 1.0 | 1484712#Agent700-20 | 53144#Agent700-22 | true | photographer ↔ photographer |
| 9 | NaN | 16044091#Agent700-32 | 1484712#Agent700-20 | false | composer ↔ photographer |

(Identity 0.0 is Schubert the composer — the left entity's composite text is a
symphony recording; identity 1.0 is a Franz Schubert who wrote an 1853 book on
photography.)

Practical notes: `identity.notna()` is equivalent to `match` in this dataset,
and identity values are only unique *within* a cluster. If you need "which
identity does each entity belong to," derive an entity → identity mapping from
the match rows — never read identity off a non-match row.

### Vectors are approximately, but not exactly, unit-length

OpenAI embeddings come back with L2 norm ≈ 1.0, which tempts a shortcut: for
exactly-unit vectors, a plain dot product equals cosine similarity.
"Approximately 1.0" is not 1.0, though. If small numeric differences matter —
reproducing `person_cosine` to full precision, nearest-neighbor rankings with
tight margins — normalize first (`v / np.linalg.norm(v)`) before using dot
products. Full cosine similarity (dot product divided by both norms) is always
safe on these vectors as-is.

### Many entities share one vector (dedup by string hash)

`embeddings.parquet` stores one row per unique *string*, not per entity: every
record whose person field reads "Schubert, Franz, 1797-1828" shares a single
embedding row. That is why 2,535 entities have only 185 person-field vectors.
Joins from pairs to vectors are therefore many-to-one — expected, not a data
quality problem. Corollary: identical vectors are **not** evidence of the same
person; the hard negatives above have `person_cosine` = 1.0 precisely because
their name strings (and thus vectors) are identical while the people are not.

### Documented performance numbers come from a held-out split, on scaled features

The pipeline's reported 98.51% precision / 95.37% recall was measured on a
14,930-pair test split the model never saw in training — not on this full
49,766-pair file, most of which *was* training data. Scoring the model on the
full file gives mildly optimistic numbers. Two rules for benchmarking:
evaluate on a proper held-out set, and feed the model the `*_scaled` columns —
scoring on raw columns silently costs ~8 points of recall (the classifier's
weights were learned against the scaled representation).
